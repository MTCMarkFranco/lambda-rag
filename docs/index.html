a primer onlambda‑rag

Decisions you can re-run in 18 months and get the same answer.

Lambda-RAG is a deterministic, legal-grade engine for evaluating documents against industry or custom policies. It separates the AI work from the deciding step — so every verdict is reproducible, cited, perturbation-proof, and defensible to a regulator.

Apache 2.0 licensed .NET 9 production codebase 8 industries · 17 corpus docs AI-free at decision time
The guarantee

Same inputs
→ same verdict
→ byte-identical
→ forever.

Runtime never calls a model. It loads a signed ruleset, projects the document into a typed graph, and evaluates each rule as a pure function over that graph.

The problem

LLMs are spectacular at reading documents — and terrible at deciding things about them.

The same prompt run twice yields different verdicts. Citations are produced by the same generative process that produced the verdict — so they can hallucinate. Trivial reordering of paragraphs flips the answer. None of these are bugs. They are inherent to the architecture: an autoregressive sampler over a high-dimensional probability distribution is not a function in the mathematical sense.

For regulator-facing review — contract review, HIPAA / GDPR / Law 25 privacy assessment, OSFI model-risk attestation, government cloud architecture review, permit assessment, pipeline-safety conformance — the deciding step has four non-negotiable obligations:

♻️

Reproduce

Same inputs → same verdict, byte-identical, forever.

📎

Cite

Every verdict points to a rule, a source span, and the exact inputs used.

🛡️

Survive perturbation

Whitespace, capitalisation, paragraph re-order ⇒ no change to the verdict.

⚖️

Be defensible

A regulator can re-run it in 18 months and get the same answer.

✕ Pure RAG-on-LLM fails all four.  ✓ Lambda-RAG was built specifically to satisfy all four.

The CLI simply tells you the rewrite path was skipped, and why.
The intellectual lineage

Not a new invention — a recombination of three settled engineering ideas.

Each idea is load-bearing. Together they make reproducibility a property of the architecture, not a feature bolted on top.

λ Typed functional evaluation

Lambda calculus. Each compliance rule is a small, pure, total function over a typed projection of the document. The runtime is, by construction, a referentially-transparent evaluator — the only known class of system that gives reproducibility for free. The "lambda" in lambda-rag is literal.

⊢ Elaboration vs evaluation

Compiler-style separation. Authoring is elaboration — typing, expansion, macro hygiene. Runtime is evaluation — running the elaborated core. The same discipline that lets a compiler emit byte-identical binaries lets lambda-rag emit byte-identical verdict reports.

⚭ Neuro-symbolic split

Decomposition. The neural side reads messy prose, surfaces candidate obligations, and writes natural-language remediation. The symbolic side makes exact, auditable, deterministic decisions over a structured representation. The handoff is the ruleset.

ⓘ  Compiler-spike provenance

This pattern was first prototyped in the internal compiler-spike repo (Python, ~Spring 2026) as a research probe: could deterministic rule evaluation match an LLM-only baseline on accuracy while gaining idempotency and citation faithfulness? The spike concluded yes on a single-vertical corpus (ARB-PSA architecture review). Lambda-RAG ports those v0.1.1 invariants to a production-grade .NET 9 codebase and extends them to 8 industries, 17 corpus documents, and an LLM-vs-runtime accuracy harness.

Lambda-RAG vs. an LLM-only review

Better at deciding — provably, not aspirationally.

An LLM is dramatically better at reading. Lambda-RAG is dramatically better at deciding, once a human-reviewed policy has been compiled into rules.

Bring your own policy

The same path that produced the 8 bundled industries — end-to-end on your machine.

There is no "import to SaaS" step. Your policy documents never leave your machine.

01 · extract

Pull a ruleset from a folder of policy documents — LLM-assisted authoring.

02 · review

Evaluate a target document against it — deterministic runtime, no LLM.

03 · promote

Optionally fold it into the regression corpus so every future build is gated on it.

# 1. Extract a ruleset from a folder of policy documents (LLM-assisted authoring)
dotnet run --project src/LambdaRag.Cli -- ruleset extract \
  --policy-folder ./my-policies/ \
  --topic-map     contract.v1 \
  --out           rulesets/my-industry/ruleset.json

# 2. Review a target document against it (deterministic runtime, no LLM)
dotnet run --project src/LambdaRag.Cli -- review \
  --document  customer-doc.docx \
  --ruleset   rulesets/my-industry/ruleset.json \
  --out       out/customer-review \
  --mode      both \
  --annotate-pass

# 3. (Optional) Promote it into the regression corpus so every future build is gated on it.
#    See README → "Promote it into the regression corpus".

If the standard topic maps don't fit your domain, clone contract.v1.json to my-industry.v1.json, list your headings & aliases, and rebuild — full instructions in the README.

What lambda-rag is not

Honest boundaries — so you deploy it where it wins.

✕Not a chatbot

It does not answer free-form questions about a document.

✕Not a rule editor

Rules cannot be hand-edited at runtime. They are re-extracted, diffed, and signed. Governance is by overlay, not by mutation.

✕Not a one-size-fits-all classifier

It needs a written policy. Where the policy lives only in someone's head, lambda-rag is the wrong tool.

✕Not better than an LLM at reading

It is dramatically better than an LLM at deciding — once a human-reviewed policy has been compiled into rules.

The neural side reads. The symbolic side decides. The handoff is the ruleset — and that boundary is the whole product.
